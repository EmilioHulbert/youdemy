Troubleshooting a desktop environment (DE) directly as `root` is a classic "power user" challenge. You are correct that logging in as root is generally discouraged for daily use due to security risks, but it is often necessary to understand how the system handles permissions and environment variables.

In many Linux distributions, including those using MATE or GNOME-based environments like Parrot, the desktop icons and session management are handled by a specific file manager component (like `caja` or `nautilus`). When logged in as `root`, this component often fails to initialize properly because it may be trying to access user-level configuration files or is being restricted by security policies like Polkit or D-Bus.

Here is how we can troubleshoot this like power users using the terminal.

---

### 1. Check for Session Errors

Since the loading is slow, the first step is to see what the system is complaining about during the login process. Open a terminal and run this command immediately after logging in as `root` to see recent errors:

```bash
journalctl -b -p err

```

* **What to look for:** Look for lines related to `dbus`, `polkit`, `caja`, or `gsettings`. This will often point to a "Permission Denied" or "Timeout" error that explains the delay and the failure to load desktop icons.

### 2. Verify File Manager Integration

The desktop icons are managed by the desktop shell (for MATE, it's `caja`). If `caja` isn't launching, the desktop will be blank. Try manually launching it from the terminal to see if it spits out errors:

```bash
caja --no-desktop &

```

If you get error messages about "D-Bus" or "X11", it confirms that the root user’s environment isn't properly initialized for a graphical session.

### 3. Check for Desktop Configuration

Often, the setting that tells the file manager to "manage the desktop" is a simple boolean toggle in the configuration database. You can query this directly:

```bash
# Check if desktop management is enabled
gsettings get org.mate.background show-desktop-icons
# Or, if using a newer/different environment:
gsettings get org.gnome.desktop.background show-desktop-icons

```

If this returns `false`, force it to `true`:

```bash
gsettings set org.mate.background show-desktop-icons true

```

### 4. Inspect Permission Mismatches

Even as root, graphical applications sometimes try to write to a user's hidden configuration folder that they don't have access to or that has corrupted permissions. Check the ownership of your configuration files:

```bash
ls -ld /root/.config
ls -ld /root/.cache

```

If these are owned by a different user (e.g., your standard account), the graphical shell may hang while trying to read/write them. Ensure they are owned by `root`:

```bash
chown -R root:root /root/.config /root/.cache

```

### 5. Why is it slow? (The "Root-Specific" Lag)

The lag you are experiencing is likely **D-Bus or network-service timeouts**. Graphical environments often expect a full user session environment (with `systemd --user` instances, pulseaudio, etc.). When you log in as root, the system might be trying to launch services that are intended for standard users, and they hang until they reach a timeout period.

* **Pro-Tip:** Check if your `/root` directory has a massive number of files in hidden folders like `.cache/thumbnails`. Sometimes, the system tries to index these as soon as you log in.
* Run `du -sh /root/.cache/*` to see if anything is unusually bloated.

### The Power User Path to Resolution

To fix this, you don't want a new D-Bus; you want to "hijack" the one already running for your GUI session.

#### 1. Identify the correct D-Bus address

In your current graphical session (where you are logged in), find the D-Bus address being used by the desktop. Run this from a terminal **inside** the desktop session:

```bash
# This will show you the exact DBUS_SESSION_BUS_ADDRESS currently in use
echo $DBUS_SESSION_BUS_ADDRESS

```

#### 2. Export that address to your Root shell

Copy the output from the command above (it will look like `unix:path=/run/user/1000/bus...`). Now, in your `root` terminal, force your shell to use that **same** address:

```bash
# Replace with the actual address you got from the previous step
export DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/1000/bus 

```

*(Note: If your user ID is not 1000, use the number found in the path.)*

#### 3. Why the "No such interface" error?

When `caja` tries to start, it checks for `org.gtk.Actions`. If the D-Bus session isn't pointing to the main desktop session, `caja` assumes it's running in a "headless" or isolated environment and crashes because it can't find the desktop interface service.

#### 4. The "Brute Force" Check

If the above export still doesn't work, it means the `remac` user has locked down the D-Bus through `polkit`. To verify, run:

```bash
# See if you can communicate with the bus at all

```

If this command lists a massive wall of text, your D-Bus connection is working. If it returns an error, your terminal has no access to the graphical session's message bus.

### Why your `.profile` isn't fixing this

Your `.profile` is a **shell** configuration file. It only runs when you open a terminal or log in via a text-based console. It does not run when the Graphical Desktop Environment (DE) initializes. Because `caja` is a graphical application, it doesn't care about what is in your shell `.profile`—it cares about the **Systemd User Session**.
