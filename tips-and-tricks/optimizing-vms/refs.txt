The discrepancies you are seeing between `df`, `du`, and the actual size of your virtual disks are common when using **Btrfs** and **dynamically allocated** virtual disks.

Here is the breakdown of why this happens and how you can manage your space more effectively.

---

### 1. Why `df` and `du` Disagree

* **How `df` works:** It queries the filesystem metadata to see how much space is allocated to the filesystem. In Btrfs, `df` often accounts for space reserved for metadata, snapshots, and internal structures that `du` doesn't "see."
* **How `du` works:** It traverses the directory tree and adds up the size of files it can find.
* **The Conflict:** Btrfs is a Copy-on-Write (CoW) filesystem. It doesn't overwrite data; it writes new data to new blocks. Over time, this creates fragmentation and "metadata overhead." Furthermore, if you have snapshots, `du` will count the same data multiple times if it exists in multiple subvolumes or snapshots, whereas `df` sees the total physical space consumed by the volume.
* **Why it looks like it "lies":** With dynamically allocated virtual disks, the virtual disk image (.vdi or .vmdk) is a single large file. If you have "expanded" a disk inside a VM (e.g., using `VBoxManage`), the guest OS sees a larger partition, but the host file on your Btrfs partition only grows when the guest actually writes data into that new space. However, Btrfs might have already allocated those chunks or be holding onto them due to its CoW nature.

---

### 2. The Truth About Your Virtual Disks

When you use `VBoxManage modifyhd ... --resize 51200`, you are telling the VirtualBox virtual disk *controller* that the "ceiling" of that disk is now 50 GB.

However:

1. **Dynamic allocation** means the file on your host `/mnt` partition only grows as the guest writes data.
2. **The "Ghost" Space:** If you delete a 10 GB file *inside* the virtual machine, the guest OS marks that space as free. But the **host** (your Btrfs filesystem) still sees the .vdi file as having the same size because VirtualBox does not automatically "shrink" the file on the host just because the guest deleted files.

---

### 3. How to Actually Fix/Reclaim Space

To make your virtual disks "fit" and reclaim space, you must perform a **compaction** process. VirtualBox cannot reclaim space automatically because it doesn't know which parts of the virtual disk are truly "empty" versus just "deleted" without help.

#### Step 1: Zero out free space in the Guest VM

You need to fill all unused space in the guest VM with zeros so that the VirtualBox file on your host becomes sparse (compressible).

* **For Linux Guests:**
```bash
# Run this inside the VM
dd if=/dev/zero of=zero.file bs=1M
rm zero.file

```


* **For Windows Guests:** Use the Sysinternals tool **SDelete**:
```cmd
sdelete.exe c: -z

```



#### Step 2: Compact the disk on the Host

Shut down the VM completely, then run this command on your host:

```bash
VBoxManage modifymedium --compact "/path/to/your/disk.vdi"

```

This command tells VirtualBox to scan the VDI file, find all those blocks of zeros you just created, and truncate them, effectively reducing the file size on your host.

---

### Summary Checklist

* **Use `btdu`:** Instead of `du`, use [btdu](https://github.com/CyberShadow/btdu). It is designed specifically for Btrfs and will give you a much more accurate picture of how your space is actually being used by identifying shared extents and true disk consumption.
* **Don't trust `df` for thin-provisioning:** `df` will always look "scary" on Btrfs because of how it handles chunk allocation.
* **Maintenance:** Make "compacting" a regular part of your VM maintenance if you are worried about host storage.

You have inadvertently started a "fill-up-the-disk" command that will not stop on its own.

### 1. Why it will not stop

You ran:
`dd if=/dev/zero of=zero.file bs=1M`

* **`if=/dev/zero`**: This is an infinite source of zero bytes. It never runs out of data.
* **`of=zero.file`**: You are telling `dd` to write those zeros into a file called `zero.file`.
* **No limit:** Because you did not specify a `count` or a `size`, `dd` will continue writing zeros until your filesystem is completely full (reaches 100% capacity) and returns a "No space left on device" error.

**You should stop this now** by pressing `Ctrl + C` in that terminal window.

---

### 2. Why is the size 104GB?

When you use a **dynamically allocated** virtual disk (the VDI file on your host), it behaves like a "thin-provisioned" file.

* When you create a 100GB virtual disk, it might only occupy 2GB on your host initially.
* As you write data into it (like you are doing now with `dd`), the VirtualBox VDI file grows on your host partition to accommodate that new data.
* By running `dd if=/dev/zero`, you are forcing every single block of your virtual disk to be "used" and filled with zeros. This forces the host VDI file to expand to its maximum allocated size because it can no longer be "sparse" (empty blocks).

---

2. **Remove the temporary file:**
```bash
rm /home/user/zero.file

```


3. **Use a smarter method:** Instead of filling the disk to the breaking point, you only need to fill the *actual* empty space. You can use the `fallocate` command or `dd` with a specific count, but a better approach for Linux guests is often using `zerofree`:
* **Install `zerofree`:** `sudo apt install zerofree`

Here is the breakdown of why your numbers look so disconnected and what is actually happening.

### 1. The "Missing" 17GB (The 99GB vs. 116GB mystery)

You see 99GB in `du` but 116GB in `df`. In Btrfs, this 17GB difference is likely caused by:

* **Snapshots and Reflinks:** If you have any Btrfs snapshots (even automatic ones from tools like `timeshift` or `snapper`), `du` only counts the file once, but the underlying blocks are held by the snapshot.
* **Metadata and Data duplication:** Btrfs tracks metadata overhead and file fragments. Because you have many large, dynamic VM files, the file system is tracking significant "slack" space.
* **The "Deleted" Data:** If you have deleted large files recently, Btrfs might not have fully reclaimed those extents yet if they are still pinned by open file descriptors or active subvolumes.

### 2. Is "Actual Size" the maximum?

**Yes.**

* **Virtual Size:** The size of the "virtual hard drive" inside the Guest OS (e.g., Windows sees a 50GB disk).
* **Actual Size:** The size of the `.vdi` file on your **Host** Linux machine.
* When you set a disk to 50GB, it means the Guest can never grow beyond 50GB. However, because it is **dynamically allocated**, it starts small (e.g., 2GB) and grows as you add files. **Once it hits 50GB, it stops growing, even if the host has more space.**

### 3. Why does Windows report 2.79GB free?

In your screenshot, the Windows Guest sees a 50GB disk, and it says 2.79GB is free. This means your Windows internal file system is nearly full.

* Because the Guest is almost full, the `.vdi` file on your Host has grown to its maximum capacity (50GB).
* **Crucially:** Even if you delete 10GB of files inside Windows, **the `.vdi` file on your host will remain 50GB.** VirtualBox does not automatically shrink the file when you delete files inside the VM. It only knows how to expand.

### 4. How to reclaim this space

To get that space back, you must tell VirtualBox to "shrink" the files.

#### Step A: Zero-fill the Guest (Do this for each VM)

You must fill the "free" space inside the VM with zeros so that the `.vdi` file can recognize the empty blocks.

* **Inside Windows:** Download [SDelete](https://learn.microsoft.com/en-us/sysinternals/downloads/sdelete). Run this command in CMD: `sdelete.exe -z c:`
* **Inside Linux:** Run `dd if=/dev/zero of=zero.file bs=1M; sync; rm zero.file`

#### Step B: Compact the file on the Host

Once the VM is powered off, run this command on your host terminal:

```bash
VBoxManage modifymedium --compact "/mnt/VirtualBox VMs/Windows 10 Enterprise/Windows10-Enterprise.vdi"

```

* **What this does:** It scans the `.vdi` file. Any block that is entirely "zeros" (which you just created in Step A) is removed from the file, and the file size on your `/mnt` partition will physically shrink.
